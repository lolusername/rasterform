Development plan for Rasterform · November 12, 2026 · baseline `72c153f`

Use functional programming to make each calculation understandable from its inputs, and use category theory to state what must agree when data crosses representations. Apply those ideas while repairing the six confirmed defects. Judge the result by whether another developer can safely make the next change. The existing Vue, TypeScript, Three.js and Electron architecture already supports this approach.

This is proposed implementation work. The affected source definitions still match the November 10 audit. That audit passed 442 tests while finding failures in builds, exported files and editor behavior. Reproduction details and research context are in the [maintainability review](MAINTAINABILITY.md).

Repeated agent edits can accumulate redundant code even with quality instructions. Later work also becomes harder when earlier changes leave broken behavior behind. These findings support preserving earlier behavior and evaluating a follow-up change as separate acceptance criteria. The plan below is an engineering recommendation drawn from those findings. [SlopCodeBench](https://arxiv.org/abs/2603.24755v2) · [SWE-Maintain](https://arxiv.org/abs/2610.14768)

**Make data ownership and effects explicit.** A pure function returns the same result for the same input values and leaves caller-owned inputs intact. Rasterform's field and mesh calculations can follow that contract. Vue reactions, GPU resources, clocks, filesystem operations and Electron messages need explicit owners because their behavior depends on the outside world. The distinction between a value and the computation that produces it explains why reading a live camera twice can differ from using one captured camera. [Moggi, *Notions of computation and monads*](https://maxsnew.com/docs/moggi91.pdf)

| Responsibility | Existing code to build on | Development rule |
| --- | --- | --- |
| Authored state | `EditorDocument`, `cloneEditorDocument` | Capture settings and camera at the start of an export. Share source pixels as immutable assets. |
| Field and geometry calculations | `composeChannelStack`, `buildMesh`, `sampleColor`, `inspectTopology` | Pass every behavioral input explicitly. Document units, color space and buffer ownership. |
| Rendering and interaction | `App.vue`, `ThreePreview.vue` | Execute a deliberate camera policy and own GPU creation, updates and disposal. |
| Native completion and persistence | `NativeLongExportLifecycle`, `createEditorSessionPersistence` | Retain job identity, ordered writes, cancellation and cleanup as explicit operational contracts. |

The current document clone deliberately shares image bytes to avoid copying them on every slider edit. The motion engine supports writing into a caller-owned frame buffer. Keep those ownership rules clear. Local mutation of a private output buffer is compatible with a stable value-based interface. Copy at the point where another owner needs an independent snapshot. Caches require the same care, since a cache keyed by image identity relies on the pixels staying immutable. **Turn mathematical laws into acceptance tests.** Category theory describes composition and agreement between paths. Here, a path might transform a mesh into GLB bytes and then decode the saved geometry. Specify an independent expected result before testing that path. Composition keeps the order of operations. Grouping pure functions differently is safe, while exchanging blur and quantization can change the picture. [Fong and Spivak, *Seven Sketches in Compositionality*](https://ocw.mit.edu/courses/18-s097-applied-category-theory-january-iap-2019/resources/18-s097iap19textbook_pdf/)

| Law to preserve | Meaning in Rasterform | Check at the boundary |
| --- | --- | --- |
| Save and reopen preserve the document | `parse(await serialize(d)) ≈ d` for a supported project | Compare authored values and asset bytes, including older project fixtures. Define numeric tolerances and compare contents across new object identities. |
| An adapter preserves the intended geometry | Decoded wireframe segments equal the triangle mesh's edges | Compare unordered endpoint pairs in a common coordinate system, including diagonals. Check collapsed lines separately. |
| A preset changes its declared fields | The camera before and after a preset is equal | Apply the preset after a manual orbit and zoom in the actual editor. |
| A captured export uses one design | Later edits cannot change an in-progress capture | Start export, edit the live document, then inspect the completed output. |
| Save completion requires both events | Packaging complete and native write complete belong to the same job | Exercise either event order, interruption, cancellation and stale job IDs. |

Use the existing Vitest fixtures and GLB decoder. Enumerate the five motion values. Add generated inputs when a larger input space warrants them, keeping an independent expected result and a reproducible seed. Mathematical laws make particular properties testable. Human comprehension and future change cost still need direct observation. [Existing GLB tests](../src/lib/export.test.ts) · [QuickCheck](https://research.chalmers.se/en/publication/237427)

**Implement in this order, with one reviewable commit per numbered item.** Each commit should contain its regression case, the fix and any affected contract documentation.

1. **Restore clean builds.** Add the matching Three.js declarations to the root development dependencies and lockfile. A disposable install of `@types/three@0.180.0` already cleared both failures during the audit. Finish when clean installs pass `npm test`, `npm run build` and `npm run desktop:check`. Use Node compatible with both package manifests. [Root manifest](../package.json) · [Desktop manifest](../electron/package.json)

2. **Give motion names one authoritative definition.** Derive `LivingFormBehavior` from the existing value tuple, and use that definition in project parsing, motion validation and the desktop download recognizer. Choose a shared location that imports only data and types so Electron validation stays independent of rendering. Keep existing exports compatible while moving ownership. The native boundary must validate origin, filename and job owner. Finish when all five names pass through filename creation and recognition, an unknown name is rejected, version-1 projects reopen, and an Expand ZIP completes with the correct UI status in real Electron. Exercise the two completion orders in the existing lifecycle tests. [Behavior tuple](../src/lib/living-form.ts#L9) · [Type](../src/types.ts#L26) · [Project reader](../src/lib/editor-document.ts#L134) · [Native recognizer](../electron/main-helpers.ts#L14)

3. **Establish the vertex-color contract.** Specify `MeshData.colors` as linear RGB. Use the existing `srgbToLinear` conversion when sampling source-image color, before interpolation. Audit all producers and consumers of this buffer so each path applies the conversion exactly once. Keep height-channel calculations governed by their own documented interpretation. Finish when a uniform `#808080` image produces approximately `0.21586` in the exported GLB color attribute, mixed-pixel interpolation is correct, and Photo, gradient, clay, texture and Blender handoff checks pass. Record that reopened Photo projects will display the corrected midtones. [Sampler](../src/lib/mesh-sampling.ts#L4) · [Conversion](../src/lib/channels.ts#L12) · [Geometry assembly](../src/lib/three.ts#L79)

4. **Encode wireframe edges explicitly.** Convert triangle connectivity to line segments for the export adapter. Reuse the current geometry pipeline and Three.js primitives, with the source mesh retained for later rendering. Finish when the decoded line set matches an independently specified quad, a raised relief and a layered Strata fixture. Cover indexed and expanded vertices, layer boundaries, collapsed segments, materials and disposal. Reuse the existing GLB decoder and binary-export tests. [GLB encoder](../src/lib/export.ts#L31) · [Export tests](../src/lib/export.test.ts)

5. **Make camera fitting a deliberate editor action.** Use the existing promise that presets preserve the authored camera. Route a preset through a document transformation whose inputs include prepared channel values, then apply that change through the current history mechanism. A mesh rebuild must receive enough context to distinguish a preset from a request to fit a changing Strata stack. Prefer the existing camera snapshot and Fit functions. Finish when orbit, zoom and target survive a preset and its undo/redo, while explicit Fit and documented mode/stack changes still frame correctly. Exercise the UI and comparison workflow to catch reactive effects. [Preset application](../src/App.vue#L1715) · [Mesh rebuild](../src/components/ThreePreview.vue#L239) · [Editor contract](EDITOR_UX.md#L37)

6. **Check topology at vertices as well as edges.** Extend `inspectTopology` to inspect the incident face fan around each used vertex. A closed manifold vertex needs one cycle. Report non-manifold vertices in mesh health and include them in STL eligibility. Finish when two tetrahedra sharing one vertex fail, one tetrahedron and two disjoint closed shells pass, and the existing valid sliver, open-surface, Text and Strata cases retain correct classifications. Construct adjacency once and measure the check on a high-detail mesh. Keep the report precise about the predicates it checks, including the scope of any self-intersection analysis. [Topology check](../src/lib/topology.ts#L39) · [Topology tests](../src/lib/topology.test.ts) · [Mesh health](../src/App.vue#L2668)

Items 2–6 depend on restored build checks. The ordering groups repairs by their existing code boundaries. Build and stage the desktop app before browser interaction checks because staging can cause a development-server reload. At the end, run the complete inherited suite, both build checks and the affected native export and editor workflows. A future release also follows the existing desktop release checks. [Verification instructions](EDITOR_UX.md#L47) · [Desktop release checks](DESKTOP.md#L125)

**Use each fix to reduce the number of decisions a reader must discover.** Extract a module when it owns a rule that changes independently or makes a meaningful calculation directly testable. Keep the shared rule easy to find and remove its superseded copies. Explain any new abstraction or dependency through its current callers and the work it saves. Existing result unions can represent mutually exclusive outcomes such as saved and cancelled. Independent completion events still need their individual state. This follows the information-hiding approach of organizing modules around design decisions. [Parnas, *On the Criteria To Be Used in Decomposing Systems into Modules*](https://prl.khoury.northeastern.edu/img/p-tr-1971.pdf)

**Evaluate one follow-up before expanding the process.** After item 2, use a disposable branch to add a temporary motion name through validation, project persistence and export recognition. A fresh reviewer should be able to locate the shared definition, explain the native checks and complete the extension using repository context. Record completion and review time, missed consumers, regressions and model cost. Then repeat this observation on the next actual feature. Use those results to decide which harness instructions and checks earn continued maintenance.

For each future change, give the coding agent the requested behavior, its current owner, the relevant existing test command and one observable acceptance condition. Review the diff for duplicated rules, unexplained layers and weakened failure handling. Ask the handoff to identify the next place a developer would edit and the evidence that the existing behavior still works.
